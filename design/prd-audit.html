1. Ringkasan Eksekutif

Psikonutrisense adalah aplikasi Android (Kotlin + Jetpack Compose) dengan backend Laravel, untuk memantau tumbuh kembang balita dan kesejahteraan psikososial ibu di Kelurahan Ngeposari sebagai bagian dari intervensi pencegahan stunting. Dari 17 layar yang didesain, 11 sudah punya alur data end-to-end (splash → login → data ibu/anak → antropometri → imunisasi → resep), sementara 6 layar lain masih berupa tampilan statis tanpa form yang tersambung ke database — Kondisi Kesehatan, Riwayat Menyusui & MPASI, Asupan Pangan, Pangan Favorit, Kondisi Psikososial Ibu, dan Tujuan Utama.

Audit skema menemukan bahwa struktur data untuk modul gizi (nutrition_records) dan psikososial (mother_wellbeing_screenings) sudah ada namun tidak cocok dengan field yang ditampilkan di desain — beberapa kolom terlalu digeneralisasi (satu skor gabungan, padahal desain minta rincian per pertanyaan), dan dua modul (Kondisi Kesehatan, Tujuan Utama) tidak punya tabel sama sekali. Rincian lengkap ada di bagian 4.

1.1 Silang-cek dengan Dokumen Kebutuhan Awal

Dokumen ISIAN_PLATFORM_DIGITAL_PSIKONUTRISENSE_dengan_Imunisasi (47 item pertanyaan, Modul A–G) adalah spesifikasi tertulis sebelum desain dibuat. Membandingkannya dengan 17 desain aktual menghasilkan 3 temuan baru yang memperkuat/melengkapi audit ini:

Konfirmasi: 6 layar yang belum tersambung memang satu wizard berurutan, bukan menu tersebar
Dokumen ini memuat contoh alur isian dengan urutan eksplisit: Data Ibu → Data Anak → Data Kelahiran → Riwayat Kesehatan Anak → Riwayat Menyusui & MPASI → Asupan Pangan Anak → Pangan Lokal Favorit → Kondisi Psikososial Ibu → Dukungan Keluarga → Tujuan & Harapan. Ini persis cocok dengan urutan penomoran desain #08→#19, memastikan diagram alur di §3 bukan tebakan.
Ditemukan langkah "Data Kelahiran" tersendiri — memperkuat rekomendasi §4.1
Dokumen sumber memisahkan "Data Kelahiran" sebagai langkah ke-3 yang berdiri sendiri, terpisah dari "Data Anak" (langkah 2) maupun pengukuran bulanan. Ini menguatkan rekomendasi P0: jenis_persalinan & usia_kehamilan_minggu sebaiknya jadi bagian dari data anak yang diisi sekali, sesuai maksud aslinya — bukan tercampur ke form Antropometri berulang seperti di desain #10.
Modul F (Sanitasi) — kebalikan dari modul lain: tabel sudah ada, desainnya yang belum dibuat
Modul F di dokumen sumber (sumber air minum, jamban sehat, jarak Posyandu, kepesertaan BPJS/JKN — item 44–47) sudah punya tabel sanitation_facilities lengkap di database, tapi tidak ada satu pun dari 17 file desain yang menampilkan layar untuk mengisinya. Table ini saat ini tidak terpakai (orphaned) sampai layarnya dibuat.
Modul G — fitur gamifikasi & komunitas sebagian besar belum dimulai
Dari 9 fitur di Modul G dokumen sumber, hanya poin & lencana ibu aktif yang sudah ada (kolom poin_ibu_aktif/lencana_aktif di mothers, tampil di Home #01). Forum Ibu Balita, Konsultasi/Chat Kader-Bidan, Video Edukasi sebagai konten dinamis, dan reminder H-3 otomatis tidak punya tabel maupun desain sama sekali — ini backlog fitur baru, bukan bug pada yang sudah ada.

4. Temuan Audit Skema Database

Tabel aktif saat ini (PostgreSQL, dibuat dari backend/database/schema_psikonutrisense.sql — bukan lewat Laravel migration): users, mothers, children, growth_records, vaccination_records, nutrition_records, pmt_logs, mother_wellbeing_screenings, sanitation_facilities, local_recipes.

4.1 Data kelahiran salah tempat (desain #09 vs #10)

Berat/panjang lahir sudah benar di tabel children, tapi desain menambahkan 2 field kelahiran baru di layar Antropometri (recurring), bukan di layar Data Diri Anak (sekali isi)
Desain #10 menampilkan Persalinan (Normal/Caesar) dan Usia Kehamilan saat lahir di form yang sama dengan pengukuran bulanan. Karena kedua data ini adalah atribut kelahiran (hanya benar diisi satu kali seumur hidup anak), menaruhnya di form yang diulang tiap bulan akan membuat data itu tertimpa/duplikat setiap kali ibu menimbang anak.

Rekomendasi: tambahkan kedua kolom ini ke tabel children (satu tempat, satu kali isi), bukan ke growth_records. 
ALTER TABLE children
  ADD COLUMN jenis_persalinan VARCHAR(20) NULL,       -- 'Normal' | 'Caesar'
  ADD COLUMN usia_kehamilan_minggu INT NULL,           -- mis. 39
  ADD COLUMN status_kepemilikan_kia BOOLEAN DEFAULT FALSE;

4.2 nutrition_records tidak mewakili 3 layar desain (13, 14, 15)

Satu tabel generik dipakai untuk 3 kebutuhan data yang berbeda bentuk
  • Desain #13 (Menyusui & MPASI) butuh status menyusui saat ini (bukan cuma ASI eksklusif 0–6 bln), jenis MPASI (checklist multi-pilih: Bubur Tim/Makanan Lumat/Makanan Keluarga), dan frekuensi camilan — ketiganya tidak ada kolomnya.
  • Desain #14 (Asupan Pangan) butuh frekuensi per kelompok pangan (nasi/bubur, hewani, nabati, sayur, buah, susu) — saat ini cuma ada 1 kolom frekuensi_protein_hewani_per_minggu, 5 kelompok lainnya tidak tertampung.
  • Desain #15 (Pangan Favorit) butuh multi-pilih dari daftar tetap (Daun Kelor, Jagung, Ubi Jalar, Tahu/Tempe, Ikan, Kacang Hijau, + teks bebas "Lainnya") — kolom saat ini pangan_lokal_favorit VARCHAR(255) cuma teks bebas satu baris, tidak bisa menyimpan pilihan checklist dengan rapi.
-- Perbaikan nutrition_records: pisah jadi field yang eksplisit
ALTER TABLE nutrition_records
  ADD COLUMN masih_menyusui BOOLEAN DEFAULT TRUE,
  ADD COLUMN jenis_mpasi_json JSONB NULL,              -- ["Bubur Tim","Makanan Lumat"]
  ADD COLUMN frekuensi_camilan_per_hari INT DEFAULT 0,
  DROP COLUMN pangan_lokal_favorit,                     -- pindah ke tabel baru di bawah
  DROP COLUMN frekuensi_protein_hewani_per_minggu;      -- pindah ke tabel baru di bawah

-- Tabel baru: frekuensi per kelompok pangan (desain #14)
CREATE TABLE food_group_frequencies (
    id BIGSERIAL PRIMARY KEY,
    child_id BIGINT NOT NULL REFERENCES children(id) ON DELETE CASCADE,
    tanggal_pencatatan DATE NOT NULL,
    nasi_bubur VARCHAR(20) NOT NULL,      -- '1-2 kali' | '2-3 kali' | dst.
    lauk_hewani VARCHAR(20) NOT NULL,
    lauk_nabati VARCHAR(20) NOT NULL,
    sayur VARCHAR(20) NOT NULL,
    buah VARCHAR(20) NOT NULL,
    susu VARCHAR(20) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Tabel baru: bahan pangan favorit, multi-pilih (desain #15)
CREATE TABLE favorite_local_foods (
    id BIGSERIAL PRIMARY KEY,
    child_id BIGINT NOT NULL REFERENCES children(id) ON DELETE CASCADE,
    bahan_json JSONB NOT NULL,             -- ["Daun Kelor","Jagung","Ubi Jalar"]
    bahan_lainnya VARCHAR(255) NULL,       -- isian "Lainnya" jika dicentang
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

4.3 mother_wellbeing_screenings menyimpan skor gabungan, desain minta skor per item (17, 18)

Skor tunggal (epds_skor_5item, skor_dukungan_keluarga) menghilangkan detail yang desain tampilkan satu per satu
Desain #17 menampilkan 4 pertanyaan skala 0–4 secara terpisah (cemas berlebihan, mudah lelah, sedih tanpa sebab, didukung keluarga) — bukan satu angka gabungan. Desain #18 merinci dukungan keluarga menjadi 3 dimensi (Emosional, Informasi, Praktis), masing-masing 0–4. Skema saat ini tidak bisa menyimpan histori jawaban per pertanyaan, sehingga tidak bisa dianalisis item mana yang memburuk dari waktu ke waktu (kegunaan utama skrining psikososial berkala). 
ALTER TABLE mother_wellbeing_screenings
  ADD COLUMN skor_cemas_berlebihan SMALLINT CHECK (skor_cemas_berlebihan BETWEEN 0 AND 4),
  ADD COLUMN skor_mudah_lelah SMALLINT CHECK (skor_mudah_lelah BETWEEN 0 AND 4),
  ADD COLUMN skor_sedih_tanpa_sebab SMALLINT CHECK (skor_sedih_tanpa_sebab BETWEEN 0 AND 4),
  ADD COLUMN dukungan_emosional SMALLINT CHECK (dukungan_emosional BETWEEN 0 AND 4),
  ADD COLUMN dukungan_informasi SMALLINT CHECK (dukungan_informasi BETWEEN 0 AND 4),
  ADD COLUMN dukungan_praktis SMALLINT CHECK (dukungan_praktis BETWEEN 0 AND 4),
  DROP COLUMN epds_skor_5item,             -- diganti 3 kolom skor_* di atas + tetap simpan kategori
  DROP COLUMN skor_dukungan_keluarga;      -- diganti dukungan_emosional/informasi/praktis

4.4 Dua modul tanpa tabel sama sekali (11, 19)

Kondisi Kesehatan & Tujuan Utama tidak punya representasi database
Desain #11 (riwayat rawat inap, sakit 3 bulan terakhir, alergi, status imunisasi ringkasan) dan #19 (tujuan program, harapan bebas teks, kesediaan ikut intervensi) sama sekali tidak punya tabel. Ini bukan perluasan tabel yang ada — perlu tabel baru. 
CREATE TABLE health_conditions (
    id BIGSERIAL PRIMARY KEY,
    child_id BIGINT NOT NULL REFERENCES children(id) ON DELETE CASCADE,
    pernah_dirawat_rs BOOLEAN DEFAULT FALSE,
    sering_sakit_3bulan BOOLEAN DEFAULT FALSE,
    alergi_makanan_obat BOOLEAN DEFAULT FALSE,
    keterangan_alergi VARCHAR(255) NULL,
    status_imunisasi_ringkasan VARCHAR(30) DEFAULT 'Lengkap', -- 'Lengkap' | 'Belum Lengkap' | 'Tidak Lengkap'
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE main_goals (
    id BIGSERIAL PRIMARY KEY,
    mother_id BIGINT NOT NULL REFERENCES mothers(id) ON DELETE CASCADE,
    tujuan_utama VARCHAR(100) NOT NULL,           -- mis. 'Anak sehat & tidak stunting'
    harapan_untuk_anak TEXT NULL,
    bersedia_ikut_intervensi BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

4.5 Field yang sudah benar, tidak perlu diubah

users, mothers, children (inti), growth_records, vaccination_records, local_recipes
Struktur inti ini sudah cocok dengan desain #01, #02, #08, #09, #16, #04, #05 dan sudah diverifikasi lewat testing CRUD end-to-end. Termasuk juga perbaikan keamanan yang sudah diterapkan sebelumnya (isolasi data per user pada growth_records & vaccination_records).
